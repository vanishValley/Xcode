# Prompt Change Evaluation

通过可复现的行为评测验证 Prompt 修改，避免根据单次输出或主观感受判断效果。

## 适用范围

- 修改 System Prompt、Agent 指令或任务模板。
- 修复工具选择错误、格式不稳定、步骤遗漏或误触发。
- 比较两个 Prompt 版本，或者检查一次修改是否引入行为回退。

普通文案润色，以及根因明确位于工具实现或业务代码的问题，不使用本 Skill。

## 工作流

### 1. 定义修改契约

修改前明确：

- 希望改善的目标行为。
- 必须保持的原有行为。
- 本次不处理的问题。
- 可以观察和判断的成功标准。

避免使用“效果更好”这类无法验证的目标。

### 2. 确认调用链和根因

定位 Prompt 的定义、拼接、变量替换和最终消息角色，并检查它与工具描述、上下文注入及模型参数的关系。先确认问题确实来自 Prompt，避免通过增加指令掩盖实现缺陷或上下文缺失。

### 3. 建立最小评测集

优先复用现有测试；否则准备少量代表性用例：

- 正例：修改后应该改善的行为。
- 反例：不应该触发新行为的场景。
- 回归例：修改前已经正确、修改后必须继续正确的行为。
- 必要时增加一个边界或歧义场景。

为每个用例定义可观察结果，例如是否选择正确的 Tool 或 Skill、是否完成必要步骤、是否遵守输出约束。不要把固定措辞或整段文本匹配作为主要判断标准。

### 4. 记录修改前基线

在修改 Prompt 前运行同一组用例，记录通过情况、实际工具选择和明显偏差。如果环境无法运行基线，明确标记为“未验证”，不要假设原有行为。

### 5. 实施最小修改

- 只修改实现目标所需的 Prompt 内容。
- 避免同时调整模型参数、工具实现和业务逻辑，以便判断效果来源。
- 删除重复、模糊或相互冲突的指令。
- 优先描述目标和判断标准，不为单个案例持续堆积特殊规则。
- 保持用户意图以及原有权限和安全边界不变。

如果其他变量也必须修改，分开实施并分别验证。

### 6. 使用同一评测集回归

比较修改前后结果，重点检查：

- 目标行为是否改善。
- 是否出现新的误触发。
- 原有正确行为是否回退。
- Prompt 是否产生明显的上下文开销或指令冲突。

只有当目标行为改善、没有关键回归，并且新增复杂度与收益相匹配时才保留修改。出现关键回归时，优先缩小或回滚修改，再根据失败证据调整。

## 停止条件

- 无法运行评测时，不宣称修改已经生效。
- 根因不在 Prompt 时，停止继续堆叠指令并说明实际问题。
- 评测需要生产数据、付费调用或外部写入时，先取得相应授权。
- 没有可观察的成功标准时，先澄清目标。

## 输出要求

最终说明修改目标、Prompt 的具体变化、修改前后评测结果、回归或未验证项，以及保留、继续调整或回滚的结论。
